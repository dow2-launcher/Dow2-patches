Что нового в v25

  Направление линии Windows считает умножением на обратную длину (1/len · dx), Mac — делением (dx / len); в 46 % случаев

  Проверено: все проверки на миллион случаев — 0; 9 контрольных реплеев идут до конца без расхождений, включая этот.

  ошибка в EnterCriticalSection при анимации) — это именно он: главный поток игры был внутри exit(), вызванного таймером

  идут до конца; тот же прогон без protfix (DOW2_NOPROTFIX=1) обрывается таймером защиты (переход на 0xcafebabe).

  считает как Windows: на миллионе случаев 0 расхождений (было 52 504).

  запоминается относительно цели, а потом пересчитывается вслед за целью — оба раза умножением матриц. Windows складывает

  Урон действий-способностей: доли урона нормализуются умножением на 1/сумму, как в Windows (recipfix, третье место;
  на миллионе случаев было 21 %, теперь 0).
  Отключение по отдельности (для проверки): DOW2_NOPROTFIX=1, DOW2_NOARTFIX=1, DOW2_NOCDOWNFIX=1, DOW2_NORECIPFIX=1.
  Всё из v23 и раньше остаётся.

  отбрасывании дробной части получалось 5 против 6.
  Заодно прочитан весь код отбрасывания (откуда и куда летит, сколько, скольжение после приземления, подъём при
  «левитации», столкновение с соседями, удар по соседям «домино»), а места с дробной математикой, которые отличаются,
  прогнаны бок о бок. Нашлось ещё три места того же рода, тоже исправлены:
  - длительность полёта по высоте дуги: Mac делил на 29,4, Windows умножает на 0,0340136 — 45,9 % случаев;
  - дальность отброса: ((скорость × t) × t) у Mac против ((t × t) × скорость) у Windows — 0,24 %;
  - подъём при «левитации»: порядок умножений — 1,09 %.
  Сами точка и время полёта до исправления расходились в 2,5 % случаев.
  Новый модуль knockfix. Проверено бок о бок: настоящий код Windows (DOW2.exe) против кода Mac, по миллиону случаев на
  каждую из четырёх проверок, через собранный dylib — 0 расхождений. Все проверки v10–v16 повторены с новым dylib —
  0 расхождений.

  Живой матч v15 (Mac, орки, против Windows, эльдары; Ashes of Typhon, 07.11) разошёлся на кадре 491 — на первом же
  ударе в ближнем бою. До кадра 490 включительно всё совпадало. Разошлось одно число у оружия ближнего боя бойцов-орков

  4,681569099 (4 единицы последнего знака). Случайные числа на обеих сторонах те же (индекс генератора совпадает),
  разошлась именно дробная математика.
  Причина: шанс особой атаки (здесь 25 %) игра делит на бойцов отряда: 100 × (1 − (1 − шанс/100)^(1/n)), у орков n = 6.
  Windows считает степень через функцию _CIpow из msvcr80 (её SSE2-вариант на double) и вычитает 1 − p, пока результат
  ещё в двойной точности, округляя только потом. Mac звал powf — степень сначала округлялась до float, и при 1 − p
  терялось до 8 единиц последнего знака. Расходились 70,6 % всех таких шансов — то есть почти любой первый удар
  в ближнем бою сразу ломал синхронизацию. Код Mac из v15 на этих входах даёт ровно Mac-значение из матча (0x4095cf6a),
  исправленный — ровно Windows-значение (0x4095cf6e).
  Заодно проверен соседний код ближнего боя и расчёта атаки (выбор особой атаки, урон, точность, броня, дальность,
  «синхронные добивания»), и нашлось ещё два места того же рода, тоже исправлены:
  - множитель точности в степени (n − 1): Windows возводит в степень умножениями во float (std::pow(float, int) у MSVC),
    Mac — через pow в double; расходились 48,3 % случаев (начиная с куба: x³ — 22 %, x⁴ и выше — около половины);
  - «синхронное добивание» (анимация, где боец и жертва ставятся друг относительно друга): Windows складывает
    первую строку матрицы в порядке (x + z) + y, Mac по-своему; расходились 8,3 % случаев (позиции бойцов).
  Новый модуль meleefix. Проверено бок о бок: настоящий код Windows (DOW2.exe и сама msvcr80.dll) против кода Mac,
  по миллиону случаев на каждую из трёх проверок, через собранный dylib — 0 расхождений. Все проверки v10–v15
  повторены с новым dylib — 0 расхождений.
  Всё из v15 и раньше остаётся.

Что было в v15
  Живой матч v14 (Mac, орки, против Windows, эльдары; Green Tooth Gorge, 03.11) разошёлся на кадре 506 (заметили на 507;
  до кадра 505 включительно всё совпадало). Разошлось одно число: высота точки, где оглушающая граната орка

  Причина — тот же класс, что раньше: где отрезок полёта снаряда пересекает рельеф, игра считает по треугольникам клетки
  карты высот. Windows (компилятор MSVC с «быстрой» математикой) складывает скалярные произведения в своём порядке
  (z + y) + x, Mac — по исходнику (x + y) + z, и точка попадания отличается в последнем бите. Так же отличались нормаль
  рельефа в точке попадания и ещё три величины рядом (расстояние до точки попадания и доля пути до неё, в том числе для
  отвесного падения) — по ним игра выбирает и сортирует, во что попал снаряд.
  Прогнано бок о бок (настоящий код Windows — DOW2.exe / SimEngine.dll — против кода Mac, по миллиону случаев):
  - точка/нормаль попадания в рельеф (HeightMapCollision::Intersect) — до 16,1 % случаев расходились, после 0;
  - расстояние до точки попадания — 17,4 %, доля пути — 26,7 %, доля пути при отвесном падении — 26,7 %; после — 0.
  Исправлено (новый модуль terrhitfix): Mac выполняет код Windows для проверки клетки рельефа (переведён в C один к одному),
  и три суммы в запросе к рельефу теперь в порядке Windows. Это касается всего, что попадает в землю: гранаты, артиллерия,
  ракеты и всё, что падает на землю (и на воду).
  Строки «math self-test: sin/cos/tan differs from Windows in 2–3 of 312 inputs» в логе — не ошибка игры: все такие входы —
  огромные числа (1e93, 1e299, максимальное double), где и сама Windows-библиотека считает старой командой процессора x87,
  а Rosetta на Mac с M1 эмулирует её чуть иначе. Углы в игре таких значений не бывают (обычные — до нескольких тысяч).
  Теперь строка в логе прямо это и говорит («all |x| >= 86016 ... harmless»).
  Все проверки v10–v14 повторены с новым dylib — 0 расхождений; dylib загружен и проверен на Linux.
  Всё из v14 и раньше остаётся.

Что было в v14
  Живой матч v13 (Mac против Windows, 03.11) разошёлся на кадре 3393: у орка-стрелка (ork_shoota_boy) после очереди
  счётчик «очередей до перезарядки» на Windows стал 0, а на Mac 4294967295. Причина — не дробная математика, а разница
  в коде: после очереди игра уменьшает этот счётчик на 1; Windows не даёт ему уйти ниже нуля (знаковое сравнение), а Mac-порт
  просто вычитает 1 из беззнакового числа. Когда оружие начинает очередь со счётчиком 0 (свежее оружие после мгновенной
  установки или перезарядка, прерванная приказом «не стрелять»), Windows оставляет 0, а у Mac получается 4294967295 —
  дампы синхронизации сразу различаются, а дальше это оружие на Mac больше никогда не перезаряжается.
  Исправлено (новый модуль weaponfix), и заодно проверена вся логика оружия: очередь, перезарядка, остывание, замах
  и затухание, установка/свёртывание, повороты турели, ближний бой; пехота, техника, турели, станковое оружие,
  гарнизоны — у всех один и тот же код. Каждое место, которое пишет эти счётчики и состояния оружия, прогнано бок о бок:
  настоящий код Windows (DOW2.exe) против кода Mac, по миллиону случаев (17 проверок). Нашлось ещё два места того же рода
  (знаковое против беззнакового), тоже исправлены:
  - длина очереди: «не меньше 1 тика» — 16,7 % случайных случаев расходились (в игре — только при необычных данных);
  - ручной огонь (заданное число выстрелов, например у артиллерии и способностей) — 22,3 % случайных случаев
    (тоже только при отрицательных или огромных числах; в обычной игре они совпадали и раньше).
  Счётчик «очередей до перезарядки» до исправления расходился в 23,9 % случаев (и в игре — каждый раз при счётчике 0). 
  После исправления все 17 проверок — 0 расхождений на всех значениях, какие бывают в игре (в трёх проверках остаются
  расхождения только на целых больше 16,7 млн тиков/выстрелов — таких в данных игры нет).
  Все переводы дробных чисел в целые (тики перезарядки, остывания, длительность очереди, загрузка чисел из описаний оружия)
  на обеих сторонах — отбрасывание дробной части, и они совпадают; формулы остывания, прогресса перезарядки, поворота
  турели и модификаторов оружия тоже совпадают бит в бит.
  Все проверки v10–v13 повторены с новым dylib — 0 расхождений; dylib загружен и проверен на Linux.

Что было в v13
  v12 чинил попадания снарядов и столкновения. В v13 — системный проход по стрельбе и проверкам дистанции: каждая
  функция прогнана бок о бок (настоящий код Windows — DOW2.exe / SimEngine.dll — и код Mac) на миллионе случайных и
  «игровых» случаев; в проверенных функциях всё, что расходилось хоть в последнем бите, исправлено и перепроверено
  (0 расхождений из 1 000 000). Проверено не всё: часть движения и крупные функции выстрела ещё в работе.
  Причина та же, что раньше: Windows-версия собрана Microsoft-компилятором с «быстрой» математикой — он складывает
  суммы и поворачивает векторы в своём порядке (а часть стрельбы считает на x87 с 24-битной точностью), Mac — по исходнику.
  Исправлено (сколько случаев расходилось до исправления):
  - система координат ствола (считается один раз на оружие, от неё зависит всё прицеливание)  — 8,9 %;
  - положение и направление дула при выстреле — 9,6 %;
  - углы на цель (поворот оружия) — 17,6 %; цель в системе координат оружия — 17,5 %;
    угол «цель в секторе обстрела» при автовыборе цели — 4,3 %;
  - разброс: куда ложится выстрел — 13,5 %;
  - точка попадания: случайная точка в коробке цели и луч к ней — 9,3 %; где луч входит в коробку цели — 3,1 %;
  - «в радиусе ли цель» (дальность оружия, ближний бой, дошёл ли отряд): расстояние между коробками юнитов — 24,6 %,
    и сама проверка складывала размеры в другом порядке;
  - снаряд, привязанный к цели (самонаведение/попадание в движущуюся цель): точка цели в системе координат цели и обратно
    — 19,9 % и 3,4 %; обращение матрицы 4x3 (общая функция, ей пользуются и другие места) — 52 %;
  - новый класс расхождений — деление на константу. Компилятор Windows вместо «x / 100» всегда считает «x * 0,01»
    (и так для любого постоянного делителя), а Mac делит честно; результаты расходятся в последнем бите у 15–64 % значений.
    Исправлено 30 мест в симуляции: проценты из описаний юнитов при загрузке (возврат ресурсов, шансы, сопротивление
    подавлению, лечение, отбрасывание, ускорение снарядов), перезарядка оружия, оценка выстрела, догоняние строя,
    порядок бойцов при движении, тики способностей, отбрасывание, минимальная дистанция шага, отдача техники, ИИ;
  - «быстрый обратный корень» (старый трюк 0x5f3759df): Windows умножает шаги уточнения в другом порядке — 20 %
    расхождений; исправлено в 6 местах (стрельба из здания, боевое и «высадка» состояния отряда, ближний бой, ИИ);
  - выбор ближайшего бойца цели к точке (дистанция складывалась в другом порядке) — 19,8 %;
  - места бойцов в здании (гарнизон) — 7,6 %; место для постройки (резерв площадки) — 6,2 %;
  - урон: доля здоровья до и после попадания (HealthExt::ApplyDamage — от неё зависит, проходит ли урон) — 24,2 %.
  Здесь Mac теперь выполняет собственный код Windows, дословно переведённый на C (как в v12), либо те же инструкции в
  порядке Windows. Проверен и сам собранный dylib (его машинный код запускался на Linux поверх кода игры Mac).
  Повторно прогнаны все проверки v10–v12 с новым dylib — без расхождений. Попутно: эталон Windows теперь считается с
  тем же режимом x87 (24 бита), что и в игре.
  Всё из v12, v11, v10, v9, v8 и v7 остаётся (включая запись контрольных сумм кадров для разбора рассинхрона).

Установка — как раньше
  Распакуй архив где угодно и дважды щёлкни dow2mac/run_vanilla.command (скрипт сам скопирует себя в ~/dow2mac).
  Если macOS не даёт запустить — правый клик → Открыть, или: xattr -dr com.apple.quarantine <папка dow2mac>

Тест (ваниль) — с подробной проверкой синхронизации:
  cd ~/dow2mac && ./run_vanilla.command -sync_high
  Хост на Windows тоже с -sync_high и с CrcTrace.dll (как для v12, утилиты: dow2win_crctrace_v12.zip). Та же карта.
  Сыграть 5–10 минут или до рассинхрона: побольше стрельбы разными отрядами, гранаты, ближний бой, ходить через укрытия.
  Выйти (Cmd+Q). Логи соберутся в ~/dow2mac/logs_vanilla_<дата>.zip — пришли его.
